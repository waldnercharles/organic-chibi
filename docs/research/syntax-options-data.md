# Syntax option sheets 1–3: unions, casts, and size and type queries

Written 2026-11-10 for the owner and the parser thread. These sheets prepare three decisions that the parser hasn't reached yet: unions (1), casts and conversions (2), and size and type queries (3). Each sheet shows what Zig, Odin, Jai, C3, Carbon and ZenC do, then lays out chibi's options with their parsing and semantic costs, recommends one and ends with the questions to answer. Every example uses only the forms settled in [decisions.md](../decisions.md), including the newly settled modules and number literals, plus the construct being decided. Parsing costs refer to [src/parser.c](../../src/parser.c) and [test/parser_test.c](../../test/parser_test.c). The parser writes nodes in *postorder*, children before their parent, into flat arrays, and it never revisits a node it has written. A form is therefore cheap when the next one to three tokens identify it (*lookahead*), and costly when the parser must change a written node's kind later (*re-tagging*) or rewind. Sources are pinned where possible: the Zig 0.15.2 language reference, Odin's docs and tag `dev-2026-11a`, C3's 0.8 docs and c3c `b2e1e99`, Carbon at `ca18985`, and ZenC's docs at `60115e0` and source at `b3f550e9`. Jai has no public documentation, so Jai facts come from the community sources in `~/Personal/jai-refs` and are marked as such. Other agents are writing sheets 4, 9 and 10 (`++`/`--`, the ternary operator, character literals, `goto`, varargs, bitfields, tasks and C import spellings) and sheets 5–8 (methods, generics, compile-time code and reflection), and each sheet below names where it depends on them.

## 1. Unions

chibi needs two different things that languages call a union. A *C union* gives all its members the same storage and records nothing about which member was written last, and C interop and the C translator need it, since hypothesis [T8](../hypotheses.md) lists "unions with C's layout" among its conditions. A *tagged union*, also called a *sum type*, holds one of several named *alternatives* plus a small integer *tag* that names the live one, and the data an alternative carries is its *payload*; games use tagged unions for events, commands and saved state, and only they can be migrated member by member when hot reload changes a layout, because only the tag says which bytes are live ([memory-models.md](memory-models.md) §5). This sheet decides how each kind is declared, whether `union` keeps meaning only C's union, and how a `switch` arm *binds* the payload, which means giving it a name the arm can use.

### Options

Options A to D decide how the two kinds are declared.

- **A. `union` stays C's union, and a tag type after a colon makes it tagged** (Zig's `union(Tag)` and `union(enum(u8))`, written in the shape of chibi's `enum Color: u8`). Without a colon, `union` means exactly C's union, so the header importer, the translator and the settled layout rule need nothing new. With a colon, the type after it is the tag. An enum type is used as the tag directly, and its member names must match the union's, as in Zig's `union(Tag)`. An integer type asks the compiler to generate the tag enum with that integer behind it, as Zig's `union(enum(u8))` does. A shared tag enum suits data-oriented code, which can keep the tags in their own array, and C APIs that already define one, such as SDL's event types. Values use the settled literal with one named member, `Shape.{ .rect = r }`, which is Zig's form too, so the expression grammar doesn't change. The cost is that one colon decides whether a hidden tag exists, so a reader has to notice it, and the same is true of Zig's `(enum)`. Parsing needs no new token, because `union` is already reserved. The parser combines `parse_enum`'s optional `: Type` with `parse_struct`'s member loop, which takes one token of lookahead after the name and about three new node kinds (start, tag and end). An alternative with no payload, such as `quit` below, is a member with no type. The struct member loop rejects that today with "expected `:` or `:=`", so tagged unions need either a bare-name member, which Zig allows, or a *unit type*, a type with only one value, which chibi doesn't have yet.
  ```
  union Bits {
      f: f32
      u: u32
  }

  enum EventKind: u8 { key, mouse, quit }

  union Event: EventKind {
      key: KeyEvent
      mouse: MouseEvent
      quit
  }

  union Shape: u8 {
      circle: Circle
      rect: Rect
  }

  e := Event.{ .key = KeyEvent.{ .code = 4 } }
  s: Shape = .{ .rect = Rect.{ .w = 2, .h = 3 } }
  ```
- **B. `union` is tagged by default, and C's union takes a marker** (Odin's `union` beside `struct #raw_union`; Zig's `extern union` is the same split seen from the other side). The safe kind becomes the short one, and Odin shows that this default works for a game-oriented language that runs at C speed. It conflicts with the plain reading of the settled layout rule, which groups unions with structs under C layout. It also makes the translator and the header importer mark every union they produce. The marker has no spelling yet, because chibi lexes `@` and `$` but has no attribute syntax, and `extern` isn't reserved, so this option waits on another decision; `extern` below is only a placeholder. Odin also names alternatives by their types (`union { i32, string }`). That can't hold two alternatives with the same payload type unless they are made distinct types, and it doesn't fit the named-member literal `.{ .rect = r }`, so chibi would keep named members either way. Parsing costs the same as A, plus whatever the marker costs.
  ```
  union Shape {
      circle: Circle
      rect: Rect
  }

  extern union Bits {
      f: f32
      u: u32
  }
  ```
- **C. `union` stays C's union, and enums whose members carry payloads are the sum type** (ZenC, and [Rust](https://doc.rust-lang.org/reference/items/enumerations.html); Carbon's `choice` is the same idea under its own keyword). One idea then covers every closed set of named cases, with or without data. `.circle` is already the settled enum-literal syntax, so a switch over a sum type reads exactly like a switch over a plain enum. A value can be built by calling its case, `Shape.circle(c)`, which already parses as a call on a field. This is ZenC's choice, and Rust programmers will find it familiar. The cost is that `enum` gets two representations. One is an integer that C understands (`enum Color: u8`); the other is a tag plus a payload, which C doesn't understand. Exported headers would need a generated struct for the second kind, and `cast(u8) shape` couldn't mean what `cast(u8) color` means. The tag also can't be an enum declared elsewhere, which loses A's shared tag. In `parse_enum`, a `:` after a member name would start a payload type. That is one more token test per member beside the existing test for `=`, plus one new node kind. Carbon's `choice` keeps `enum` simple at the cost of a new keyword.
  ```
  union Bits {
      f: f32
      u: u32
  }

  enum Shape: u8 {
      circle: Circle
      rect: Rect
      none
  }

  s := Shape.circle(Circle.{ .r = 1 })
  ```
- **D. No tagged-union syntax; compile-time code builds them** (Jai's `Tag_Union`, The Way to Jai §26.17). The language keeps only C's union, and a library function run at compile time builds a struct that holds a tag enum and a union. That puts the owner's defining feature to work, since compile-time code may create types with methods. A library can also choose layouts that the language wouldn't, such as tags kept in a separate array. The cost is that nearly every game needs sum types, so every program leans on a generator. The checker can't check payload reads, and it can check *exhaustiveness* (that every alternative has an arm) only if the generated tag is an enum and switches over enums must be exhaustive. Error messages point into generated code, and arms read payloads through fields, as in option H. The spelling below is a placeholder, because sheets 7 and 8 decide what compile-time code may produce and how it reads types.
  ```
  const Shape := tagged_union(.{ .circle = Circle, .rect = Rect })

  switch s.tag {
      .circle => total += area(s.payload.circle)
      .rect => total += s.payload.rect.w * s.payload.rect.h
  }
  ```

Options E to H decide how a `switch` arm binds the payload. Each example matches the `Event` union from option A.

- **E. A capture after the arrow** (Zig's `|x|` and `|*x|`). Each arm names its own binding, which suits arms whose payload types differ, and `|*m|` makes the pointer form explicit. After `=>`, a `|` can't start a statement, so the test costs one comparison per arm, plus one node for each capture. The cost is that `|` takes a second job beside bitwise or. An arm with several labels, such as `.key_down, .key_up => |k|`, also needs a rule, for example that all its payloads have the same type.
  ```
  switch e {
      .key => |k| press(k.code)
      .mouse => |*m| m.*.x += 1
      .quit => running = false
  }
  ```
- **F. One name for the whole switch** (Odin's `switch v in value`). The name comes before `in` and the union after it, in the shape of the settled `for x in items`. In an arm with one label, `v` has that alternative's payload type. In an arm with several labels or `_`, `v` keeps the union's type, which is Odin's rule. The parser tests for a name followed by `in` once per switch, which is a two-token test, and adds one binding node; the arms are parsed as today. Odin writes `switch &v in value` to bind a reference that the arm can modify. The cost is that one name changes type from arm to arm, which surprises some readers. `in` also can't later become a membership operator that is usable at the head of a switch.
  ```
  switch v in e {
      .key => press(v.code)
      .mouse => move_cursor(v.x, v.y)
      .quit => running = false
  }
  ```
- **G. Patterns with arguments in the label** (Carbon's `case .Some(x: i32) =>`, ZenC's `Shape::Circle(r) =>`, Rust). The binding sits beside the alternative it comes from, and the form can grow into nested patterns later, as it has in Rust and Carbon. `.key(k)` already parses as a call on an enum literal. So either `parse_switch` treats a label of the shape `.name(` as a pattern, which costs a three-token test per label, or the parser emits a call and the checker re-tags `k` from a use into a new declaration. Either way, the same text means a pattern in a label and a call everywhere else. It also invites a full pattern language with nesting and guards, which is a large feature for the checker.
  ```
  switch e {
      .key(k) => press(k.code)
      .mouse(m) => move_cursor(m.x, m.y)
      .quit => running = false
  }
  ```
- **H. No binding; arms read the payload as a field** (C, Jai, and Zig's field access on bare unions). It needs no syntax at all. The cost is that the switch head must be a name, because an arm can't read the payload of `next_event()` without a temporary. Each read such as `e.key` must also be checked at run time, unless the checker proves the tag from the enclosing arm, and any assignment to `e` inside the arm undoes that proof.
  ```
  switch e {
      .key => press(e.key.code)
      .mouse => move_cursor(e.mouse.x, e.mouse.y)
      .quit => running = false
  }
  ```

### Recommendation

**I recommend A for declarations and F for binding,** because together they add no keyword, token or expression form. Without a colon, `union` stays exactly C's union, which the layout decision, the header importer and the translator already assume. The tagged form reuses the `: Type` shape that was settled for `enum`, and its values use the settled literal. A also keeps `enum` an integer that C understands, which option C gives up, and it lets a tag enum be shared with a C API or kept in its own array. F reuses `in` and the shape of `for x in items`, costs one two-token test per switch, and leaves arm parsing alone. G, by contrast, gives one text two meanings, and E gives `|` a second job; E is the fallback if per-arm names turn out to matter. I would also fix the tagged union's layout as a C struct with the tag first and a C union of the payloads after it. An exported header can then describe it, reflection finds every tag at offset 0, and hot reload can migrate each value through its live alternative. C unions stay plain bytes, which survive a reload only when their layout is unchanged. Outside a switch, `e == .quit` can test the tag, as Zig allows because its tagged unions convert implicitly to their tag enum, which leaves the reserved `is` unused. Methods on unions follow sheet 5, generic unions such as an optional type follow sheet 6, and the reflection record for tags follows sheet 8.

### Questions for you

**Answered 2026-11-11** in the parser thread. The Unions row of [../decisions.md](../decisions.md) is the authority. In this sheet's terms:
- Question 1: A. A plain `union` is C's union, and `union Name: Tag { … }` is tagged, where `Tag` is an existing enum or an integer type.
- Questions 2 and 3: F, `switch v in e`, plus `switch &v in e` to bind a pointer to the payload.
- Question 4: a tagged union is a C struct with the tag first.
- Question 5: an alternative without a payload is a bare name.
- Question 6: a switch must be exhaustive unless it has a `_` arm.
- Question 7: `e is .key` tests the tag, using the reserved `is` instead of the `==` recommended above. Inside `if e is .key`, reading `e.key` needs no check.
- Question 8: structs may contain anonymous unions.

1. Is `union` without a colon exactly C's union, with tagged unions written `union Name: Tag { … }` (A), or is `union` tagged by default (B), or are sum types enums with payloads (C) or a library type (D)?
2. How does an arm bind the payload: once per switch with `switch v in e` (F), per arm with `=> |v|` (E), by patterns such as `.key(k) =>` (G), or not at all (H)?
3. Can a binding refer to the payload in place so that the arm can modify it, written `switch &v in e` as in Odin?
4. Is a tagged union laid out as a C struct with the tag first, or is its layout left to the compiler, as Zig does?
5. May an alternative carry no payload, written as a bare member name such as `quit`?
6. Must a `switch` on a tagged union list every alternative unless it has a `_` arm?
7. Does `e == .quit` test the tag outside a switch, or should the reserved `is` keyword do that?
8. Are anonymous union members inside structs allowed, as in C11? The translator needs them ([c-corpus.md](c-corpus.md) §4.7).

## 2. Casts and conversions

A *cast* turns a value of one type into a value of another, and it comes in three kinds. A *value conversion* keeps the number and may lose range or precision (`i32` to `f32`, `u32` to `u8`), and a *pointer cast* keeps the address and changes the type it points to. A *bit cast*, which Odin calls *transmute*, keeps the bits and reads them as another type, such as the IEEE bits of an `f32` read as a `u32`. chibi reserves both `cast` and `as`, so one spelling should win, and behind the spelling sits a policy about which conversions happen with no syntax at all, which decides how many casts translated C and game code carry ([c-corpus.md](c-corpus.md) §4.4, hypothesis [T8](../hypotheses.md)).

### Options

Options A to E decide the spelling.

- **A. Prefix keyword `cast(T) x`** (Odin, Jai). This is C's `(T)x` with a keyword in front. It keeps C's order and C's precedence, that of a prefix operator like `-x`, so the C translator only renames, and `(float)a / b` becomes `cast(f32) a / b` with no added parentheses. Reading the type first also matches the settled prefix types `*T` and `[]T`. Parsing costs one keyword case in `parse_operand` with no lookahead. That case reads `(`, a type, `)` and one operand, then emits a cast node after both children, so the postorder output is the type's nodes, the operand's nodes, then the cast. A line that starts with `cast` starts a new statement, because `cast` can't continue an expression, and `cast(T)` at the end of a line continues onto the next, because an operand must follow. The cost is that casting a compound expression needs parentheses, `cast(f32)(a + b)`, as in C. `cast(f32)` also looks like a call to a reader who doesn't know the keyword.
  ```
  ratio := cast(f32) hits / cast(f32) shots
  bytes := cast(*u8) &header
  index := cast(u16)(base + offset)
  ```
- **B. Infix keyword `x as T`** (Carbon, [Rust](https://doc.rust-lang.org/reference/expressions.html#expression-precedence); ZenC rejects it). It reads left to right and follows a field access without parentheses, as in `items.len as u32`. The right side is a type, not an expression, so `parse_binary` needs a special case beside its operator table. chibi must also choose a precedence, and the precedents disagree, because Rust binds `as` tighter than `*` while Carbon makes mixing it with arithmetic an error, which forces parentheses. The translator must move each type after its operand and add parentheses around compound operands, so `(float)(a + b)` becomes `(a + b) as f32`. A line that starts with `as` continues the previous expression, just as a line that starts with `- b` does. The modules decision renames imports with `const f := import "…"`, so `as` has no other planned use either way.
  ```
  ratio := hits as f32 / shots as f32
  bytes := &header as *u8
  index := (base + offset) as u16
  ```
- **C. Conversion call `T(x)`** (Odin's `f64(i)`, [Go](https://go.dev/ref/spec#Conversions)). For a named type the parser doesn't change, because `f32(x)` already parses as a call, and the checker treats a call whose callee is a type as a conversion. Pointer and array types can't be written there, because `*u8(p)` and `(*u8)(p)` both fail today with "use `.*` to dereference". Pointer casts would therefore need a second form. Once generic types take arguments in parentheses (sheet 6), `T(x)` also looks like a type applied to an argument, as in `List(i32)`.
  ```
  ratio := f32(hits) / f32(shots)
  ```
- **D. C-style `(T)x`** (C3, ZenC). chibi can't parse this without giving something up. `(f)(x)` is a settled call with a parser test, and `(a) - b` could be a subtraction or a cast of `-b`. C solves this by looking names up while it parses, C3 by making type names a separate kind of token, and ZenC by guessing from token shapes and rewinding. chibi's parser can't know whether a name is a type, because top-level names may be declared later and in any order. Rewinding would also mean deleting nodes already written to the postorder arrays.
  ```
  ratio := (f32)hits / (f32)shots
  ```
- **E. A cast that takes its target from the expected type** (Zig's `@intCast(x)` with `@as(T, x)`, Jai's `xx x`, Odin's `auto_cast x`). The checker already needs expected types for `.{ … }` and `.red`, so inferring a target costs no new machinery, and casts stay short where the target is obvious. The cost is that the target can't be seen at the cast, which makes translated C harder to read. A second form is also needed wherever nothing supplies a target. Zig's version is a family of builtins (`@intCast`, `@truncate`, `@floatFromInt`, `@ptrCast`), and chibi has no builtin syntax, so the `@` spelling below is hypothetical. This form could be added beside A later.
  ```
  count: u16 = @int_cast(total)
  ```

Options F to H decide how bits are reinterpreted.

- **F. A keyword, `transmute(T) x`** (Odin). It has the same shape as `cast(T) x`, so the pair is easy to learn, and searching for one word finds every bit cast. It costs one more keyword, which isn't reserved today.
  ```
  bits := transmute(u32) x
  ```
- **G. A function checked at compile time, `bit_cast(T, x)`** (Zig's [`@bitCast`](https://ziglang.org/documentation/0.15.2/#bitCast), C3's `bitcast(x, T)` macro). It needs no keyword, and the size check is ordinary compile-time code; C3's macro requires `@sizeof(expr) == $Type::size` before it compiles. Writing it as a library function needs generics (sheet 6), so it would be a function provided by the compiler under the same name until then. Passing a composite type such as `[4]u8` as an argument needs the same parser change as option C of sheet 3.
  ```
  bits := bit_cast(u32, x)
  ```
- **H. A pointer cast and a dereference** (Jai's `<< cast(*float) p`, C's `*(uint32_t *)&f`). It needs nothing new. The value must be addressable, and the parentheses below show how awkward it reads. The code also becomes undefined if chibi's optimizer ever assumes that pointers to different types never point at the same memory, which is C's *strict aliasing* rule.
  ```
  bits := (cast(*u32) &x).*
  ```

Options I to L decide which conversions are implicit. *Widening* converts to a type that holds every value of the source type (`u8` to `u32`); *narrowing* goes the other way and can lose information. In all four options a literal takes the expected type when its value fits, so `x: u8 = 200` needs no cast, as in every language here that documents its rules.

- **I. No implicit conversion between typed values** (Odin, Go). Every change of type is visible, and the rule is the simplest to state. Translated C and game code then carry a cast at every widening, including the many that can't lose anything, so the casts that matter are harder to spot.
  ```
  i: int = cast(int) handle.index
  wide: i64 = cast(i64) small
  ```
- **J. Implicit widening wherever no value can be lost** (Zig, Carbon, Jai). `u8` to `u16`, `u8` to `i16` and `f32` to `f64` need nothing, and Carbon adds `i32` to `f64`. This needs the fewest casts. However, `total: i64 = a * b` with `a, b: i32` compiles, multiplies in 32 bits and then widens a product that has already overflowed.
  ```
  wide: i64 = small
  total: i64 = a * b
  ```
- **K. Implicit widening of simple expressions only** (C3). A name, field, index, call or literal may widen, and so may a prefix operator applied to one of these; the result of a binary operator may not. `wide: i64 = small` costs nothing, while `total: i64 = a * b` is an error that asks the programmer to choose the width, as in `cast(i64) a * b`. The checker decides by looking at one node, the root of the source expression, which is the last node of its range in the postorder array. Under I, J and K alike, the translator must insert a cast wherever C's promotions would compute a different result from chibi's arithmetic, so K adds no work for it. The cost is one more rule to learn, and only one of the six languages uses it.
  ```
  wide: i64 = small
  total: i64 = cast(i64) a * b
  ```
- **L. C's rules** (C's *integer promotion*, which converts operands narrower than `int` to `int` before arithmetic, and its usual arithmetic conversions; ZenC presumably inherits them by emitting C, unverified). Translated C would need no casts. It brings C's most error-prone rules into a new language, for example `u8 + u8` having type `int` and signed values silently turning unsigned in comparisons. Of the other five languages, only C3 keeps part of them, its promotion of integers narrower than `int`.
  ```
  sum: i32 = a + b
  ```

None of I–L changes the speed of generated code, because a widening is one instruction, a sign or zero extension that fills the new high bits, whether or not the source spells it. What T8 depends on is the arithmetic itself, meaning whether overflow wraps, traps or is undefined, and this sheet doesn't decide that.

### Recommendation

**I recommend A (`cast(T) x`), G for bit casts and K for implicit conversions, and removing `as` from the keywords,** because `cast(T) x` is ZenC's `(T)x` made parseable. It has the same order and C's precedence, so translated C is renamed rather than reordered. It costs one keyword case in `parse_operand` with no lookahead, whereas `as` needs a special case beside the binary operator table and a precedence on which Rust and Carbon disagree. With imports renamed by `const`, nothing else wants `as`. Bit casts are rare and easy to get wrong, so a compile-time-checked `bit_cast(T, x)` keeps `cast` meaning "the same value" without spending a keyword. K catches the overflow that J lets through, costs the checker one node-kind test, and adds no work for the translator. I is defensible, but it buries the casts that matter among widenings that can't fail. Whether an untyped pointer converts implicitly, as C's `void *` does, belongs with the C import sheet (10).

### Questions for you

**Answered 2026-11-10** in the parser thread. The Casts row of [../decisions.md](../decisions.md) is the authority; in this sheet's terms:
- Question 1: neither A nor B. Values convert with `T(x)` (option C), structs included when their field types match in order, and both `cast` and `as` stop being keywords.
- Questions 2 and 4: pointer to pointer, pointer to integer and same-size bit changes all go through one keyword, `bitcast(T, x)` (G's shape). It rejects slices. Enums and integers convert only explicitly, as `u8(Color.red)` and `Color(n)`, and `Color(n)` checks in checked builds that `n` is a member's value.
- Question 5: K.
- Question 7: no inferred-target cast (E). The decision cites the extra wrapping it causes in Zig's arithmetic.
- Question 3: a narrowing `T(x)` such as `u8(total)` checks the range in debug and release builds. To keep the low bits, mask first, as in `u8(total & 0xFF)`, which also lets the compiler drop the check.
- Question 6: an integer converts to a float implicitly only when every value converts exactly, so `i32` to `f64` is implicit and `i32` to `f32` is not.

3. Does a narrowing `cast` check the range in debug builds (Zig, Jai) or truncate silently (C)? If it checks, the translator needs a truncating spelling for C's casts.
4. Is bit reinterpretation a function, `bit_cast(T, x)` (G), or a keyword, `transmute(T) x` (F)?
5. Which conversions are implicit: none (I), every lossless widening (J), lossless widening of simple expressions (K), or C's rules (L)?

## 3. Size and type queries

Allocators, serializers, GPU buffers and structs shared with C need a type's size, alignment and field offsets, and C code asks for them constantly, with `sizeof` appearing 9.3 times per 1,000 lines of the corpus mix ([c-corpus.md](c-corpus.md) §4.4). chibi reserves four keywords for these queries today: `sizeof`, `alignof`, `offsetof` and `typeof`. Because compile-time code is a defining feature, the first three may not need to be language features at all, since the checker already stores every type's size, alignment and offsets, and compile-time code could read them through *reflection*, which is code reading facts about types. `typeof` is different, because it has to give the type of an expression without running the expression.

### Options

- **A. Keywords** (C; ZenC's `sizeof` and `typeof`). The parser knows that a type comes next, so it can parse `*Node` or `[4]f32` there, which ordinary call arguments can't do today. The translator also copies C's `sizeof` unchanged. Since `T` and `x` are both plain names, the parser still can't tell a type from a value, and it leaves that to the checker. The option costs four keywords and four node kinds for four facts. Every later query, such as bit size, field count or enum names, then needs another keyword or a second spelling through reflection. `offsetof(T, field)` also needs a special rule for its bare field name.
  ```
  buf := alloc(sizeof(Vertex) * count)
  ```
- **B. Builtins marked by a sigil** (Zig's `@sizeOf`; C3's `$reflect` and `@sizeof`). A *sigil* is a symbol such as `@` that marks a name as special. It keeps builtins from colliding with user names, and one rule, `@name(args)`, covers every compiler *intrinsic* (a function the compiler implements itself), now and later. `@` is already lexed and unused. The cost is a new kind of name that every reader must learn, and the parser still needs types as arguments. Zig's set has grown to 118. chibi spelled Zig's `@import("…")` as the keyword expression `import "…"`, so a sigil would be new to the language.
  ```
  buf := alloc(@size_of(Vertex) * count)
  ```
- **C. Built-in names in the outermost scope** (Odin, Jai). There is no keyword and no sigil, since `size_of(Vertex)` already parses as a call, and a program may shadow these names like any other. However, `size_of(*Node)` and `size_of([4]f32)` don't parse today, because `parse_operand` accepts a type that starts with `*` or `[` only before `.{` or `.[`. Otherwise it reports "use `.*` to dereference" or "expected `.{` or `.[` after a type". Accepting a bare type as an operand is a small change, and the generics sheet (6) needs it anyway for arguments such as `List(*Node)`, but the helpful error for `* a` would then move to the checker. `offset_of` also needs a way to name a field. Odin gives its builtin a rule for a bare name, and Zig takes a string. In chibi, `.uv` already parses as an enum literal, which the checker could resolve against the type's fields.
  ```
  buf := alloc(size_of(Vertex) * count)
  uv_at := offset_of(Vertex, .uv)
  ```
- **D. Properties of the type** (C3's `Foo.sizeof` up to 0.7 and `Foo::size` since 0.8; Carbon's open `T.ByteSize`). `Vertex.size` already parses as a field access, so named types need no parser change, and the query reads like data. In chibi, though, `.` after a type already names one of its members (`Color.red`), and `.` after a package names a declaration (`geo.Point`). An enum member or a generated declaration called `size` would therefore collide with the property, which is the collision C3 removed by moving to `::` in 0.8.0. `::` is lexed but unused, so it would need a new postfix rule. Offsets would need a property on a member, which has no natural form, and `(*Node).size` doesn't parse today.
  ```
  buf := alloc(Vertex::size * count)
  ```
- **E. Ordinary compile-time library functions over reflection** (closest: Jai's `type_info(T).runtime_size` and `offset_in_bytes`, Odin's `type_info_of(T)` and Zig's `@typeInfo(T)`, though none of them defines `size_of` this way). The language keeps one primitive, the compile-time type record that the reflection sheet (8) will choose. `size_of`, `align_of`, `offset_of`, field counts and enum names then become short functions in a core package that read that record, so a new query costs no compiler work. Option R3 in [comptime-generics-reflection.md](comptime-generics-reflection.md) §7.7 already proposes one type table shared by compile-time queries and the run-time table. When a type's layout changes during hot reload, every compile-time result that read it is recomputed. The same note proposes that every compile-time result record what it read (§7.1, option A2), so sizes need no special case. The cost is that E depends on three undecided features: a reflection record, types as arguments, and calls folded to constants at compile time. It therefore can't come first. `type_of` can't be such a function, because a function evaluates its argument and `type_of(next())` must not call `next`.
  ```
  const VERTEX_SIZE := size_of(Vertex)
  buf := alloc(VERTEX_SIZE * count)
  ```

### Recommendation

**I recommend spelling the queries as plain names, `size_of`, `align_of`, `offset_of` and `type_of` (C), implementing the first three as compile-time library functions once reflection exists (E), and removing the four keywords,** because C and E look the same where they're called. Code written before the reflection sheet is decided therefore doesn't change afterwards. The compiler keeps one true intrinsic, `type_of`, which must not evaluate its operand. A freezes four facts into the grammar, and every later query would need another keyword or a second spelling. D collides with the settled meanings of `.` after a type or package name, which is the collision that pushed C3 to `::`. B pays off only if the compile-time sheet adopts a sigil for every intrinsic, and in that case `type_of` should take it. For a value, `size_of(type_of(x))`, as in Zig and Jai, keeps `size_of` taking only types and avoids Odin's rule that one name accepts both. Writing `y: type_of(x)` in a type position also needs `parse_type`, which accepts only a name, a qualified name such as `geo.Point`, or a type that starts with `*`, `[` or `fn`, to accept a call-shaped type. Generic types such as `List(i32)` need that too (sheet 6).

3. How does `offset_of` name a field: `.uv` resolved against the type's fields, a string `"uv"` (Zig), or a bare name with its own rule (Odin)?
